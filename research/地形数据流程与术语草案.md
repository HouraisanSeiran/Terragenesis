# 地形数据流程与术语草案

本草案供故障修复后讨论。它区分目标框架与当前实现，不代表每一层已经完成。

## 推荐的数据流程

Terrain Diffusion 基础高程 → 流域尺度河网与河床/水面处理 → 局部 VDM 岩壁 → 数据校验与保存 → Minecraft 体素化与方块填充。

洞穴使用独立体积场处理，不能把任意洞穴拓扑都归入 VDM。数据处理可以离线预生成，也可以由模组管理后台按区域预生成；两者应输出同一种可验证数据包。Minecraft 区块是读取与显示单位，不应成为决定流域出口的单位。

## 术语建议

| 名称 | 本工程中的含义 | 不应混用的概念 |
| --- | --- | --- |
| 基础高程图 | 每个水平位置一个地表高度，由 Terrain Diffusion 或可替换生成器输出 | 方块地图、任意三维实体 |
| 地貌区域 | 包含山脉、平地及特征地貌的一片宏观区域 | Minecraft 的生物群系注册项 |
| 生物群系 | 温度、降水、植被与方块表层等游戏生态配置 | 一种独立地形算法 |
| 流域 | 排向同一出口、具有上游下游关系的区域 | 每个区块独立画出的河段 |
| 河网 | 连通关系、河道路径及汇流量 | 水面高度图本身 |
| 河床高程图 | 河道底部的地表高度 | 水面高度 |
| 水面高程与湿区 | 水位和水实际覆盖范围，必须结合河床及岸线判断 | 给河道中心线一个高度再无限向侧面填水 |
| VDM | 相对于参考表面、具有坐标约定的 XYZ 位移数据 | 三张任意噪声图；完整洞穴体积 |
| 岩壁面片 | 局部参数化表面，可绕水平轴倾斜并产生悬挑 | 必须沿世界竖直方向投影的高度图 |
| 侵蚀 | 地表几何随水流、坡度、岩性等规则变化 | 只有收支平衡、没有地形反馈的水沙账本 |
| 体素化 | 把连续表面或体积转换为 Minecraft 方块占据状态 | 地貌布局算法 |
| 地形数据包 | 保存高程、水面、位移、来源与校验信息的工程数据 | Minecraft 数据包 datapack |
| 内置服务 | 模组自带启动管理和服务程序，负责检查、启动、等待就绪和退出清理 | 把 Python、CUDA 和模型权重全部塞进一个 JAR |

## 当前问题对应的约束

1. 悬河：水位必须受完整河谷地形约束，包含汇流处、上游起点、岸线以及体素化后的侧面。不能仅检查河中心有水，或靠抬高两岸造堤遮掩问题。
2. 全域崩溃：模组应在创建/加载全域世界前启动并检查扩散服务。服务缺失或模型不匹配时返回可读错误；不能用其他算法悄悄替代已保存世界的模型。
3. 运行时重复计算：有限地形导出后，应读取保存的高程与 VDM，避免导入 Minecraft 时再次执行侵蚀和塑形。
4. 版本变化：生成参数、模型身份、坐标比例和文件校验需要随数据保存。修复版使用新生成身份，旧存档不得在未迁移时混入新配方造成断层。

## 必须明确的实现边界

- 现有有限流域使用已烘焙的扩散样片，叠加显式山海轮廓与河网；它不等于端到端河网条件扩散模型。
- 全域扩散目前仍需要区域级流域规划，不能把有限演示的河口布局直接重复铺满世界。
- 局部岩壁水沙收支守恒不等于完整的真实流域侵蚀；降雨到崖顶的空间路由、泥沙沉积对地形的反馈需要继续实现。
- 当前环境中的 Python 虚拟环境依赖本机 Anaconda；复用它可以验证自动启动，但不能证明运行环境可搬移到其他电脑。
- 实际客户端画面与算法预览、专用服务器检查应分别报告。后两者不能代替客户端视觉验收。

世界海平面保持 Y=62，上边界为 1024（最高方块 Y=1023）。内部高程的海平面参考 72 是旧数据坐标约定，经过比例变换得到游戏高度，不是把海平面重新升高。
