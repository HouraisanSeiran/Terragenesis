# 三维河网、水沙与 Minecraft 导出设计

日期：2026-09-28。本文是工程方案；独立原型的验证不等于默认世界已接入、论文已复现或游戏视觉效果已验收。

## 表示与职责

保持原始 Terrain Diffusion 高程不变，在派生流水线中增加河网约束和局部处理。河网必须在区域加工和 Minecraft 分块之前确定。存储区域负责切片，不能各自选择河流出口。

1. 基础地形：高度图及气候、地质条件。
2. 三维河网：世界坐标 XYZ 中的节点和有向河段，节点包括源头、汇流点、落水洞、复出泉、地下湖、河口。水面、河床和洞顶分别存储，不能把路径 Y 同时解释成三者。
3. 水沙状态：流量、水深、湖泊库存、岩石损失、可移动沉积物和边界输出。先约定单位，再计算。
4. 几何处理：地表高度图，多层高度图中的固体/空腔区间，以及已有表面的 VDM 位移。新洞口、贯通和断裂交给可改变拓扑的表示。
5. 成品导出：检查水陆接触、洞顶厚度、接缝和物质预算后保存派生产物；Minecraft 查询该成品并写入方块。

管状路径范围只决定允许处理的位置及平滑权重。岩石表面还必须真正接触连通水体，才能侵蚀。不能把整条管道内的岩石都视作已被水浸润。

## 借鉴论文的具体边界

- Nilles 等（2024），[3D Real-Time Hydraulic Erosion Simulation using Multi-Layered Heightmaps](https://doi.org/10.2312/vmv.20241211)：借鉴多层柱表示、横向侵蚀、柱分裂及支撑检查。普通高度图可初始化为每个 XZ 单元一个固体区间；侵蚀后允许一列出现多个固体区间和空腔。这不是把普通高度图侵蚀公式直接换成 XYZ 位移。
- Génevaux 等（2013），[Terrain Generation Using Procedural Models Based on Hydrology](https://doi.org/10.1145/2461912.2461996)：借鉴先明确河网/流域再约束地形的组织方式。对本工程采用基础生成后规划并校正河道的形式；地下支路是另行设计的扩展。
- Schott 等（2023），[Large-scale Terrain Authoring through Interactive Erosion Simulation](https://doi.org/10.1145/3592787)：参考路径、高程约束和大尺度侵蚀协同；不能据此宣称已解决地下水动力。
- Shobe 等（2017），[SPACE 1.0](https://gmd.copernicus.org/articles/10/4577/2017/)：借鉴基岩、活动沉积层和输沙的独立收支。

2024 论文中的 virtual pipes 是相邻离散单元之间的通量计算方式，与用户提出的沿河路径扫出的几何管状影响域不是同一概念。独立原型先验证河网和收支接口；多层柱通量、柱分裂、支撑与坍塌求解仍须实现及验证。

## 地表与地下连接

先以海洋、已确定的大河水位或地下湖为下游边界，筛选地形允许的源头和河路。地表路由需识别真实洼地，选择保留湖泊、溢流或受控切沟，不能简单将每个洼地强制填平。

地下路由还需岩性、节理、最小覆岩厚度和出口位置约束；空间中随机连线即使向下，也不代表存在合理洞穴。落水洞和复出泉处允许覆岩厚度趋零，洞内段则检查完整断面上方的岩盖。过薄洞顶应另行处理天窗或坍塌，不能隐藏失败。

首版限定地下明渠：洞内有空气和自由水面，沿下游水面不升高。岩石底面可局部起伏，但通水断面不能被门槛完全堵住。先用保守的单调纵剖面验证，再增加回水、瀑布和跌坎。

地下承压管道的底部可先下降再上升，是否流通取决于压力水头和损失，不能用“每一点 Y 都必须降低”判定。承压、虹吸和明满流转换暂不纳入首版。

地下湖满足 `ΔV/Δt = Q入 - Q出 - Q渗漏 - Q蒸发`。无出路且持续进水的地下湖会积水和涨水；必须保存库存或声明有限时长，不能把它当作永久消失的流量。固定几何但可累积库存的演示也不等于已有真实湖面涨落：最终需要库容—水位关系及溢流口。

## 小溪如何合并为大河

所有支流共享同一个汇流节点的世界位置与水面高程。先解整张图上的流量，再决定宽深，再一次性处理汇流区域的河床和水体；不能各河段独立雕刻后只拼接高度图。

忽略汇流区短时蓄水时，`Q出 = ΣQ入 + Q侧向汇水 - Q损失`。面积、降雨、蒸散及入渗决定新增流量。河流级序适合命名、分级和显示，不能替代流量。

可用经过标定的水力几何关系初始化断面：

`W = W参考 × (Q / Q参考)^b`

`H = H参考 × (Q / Q参考)^f`

其中宽 W、深 H 使用明确长度单位，Q 使用体积/秒；两个指数需标定，不能当作普适常数。矩形近似时以 `U=Q/(W H)` 检查速度，复杂断面使用实际过水面积。Q=0 时不应为满足最小显示宽度而凭空生成水。

例如，仅作比例演示，取 b=0.5：两条流量相同、各宽 2 格的小溪汇合，下游宽约 `2√2 ≈ 2.83` 格，而非把河宽加成 4 格；深度和流速也随断面标定调整。进入游戏后将连续轮廓体素化，并在多个断面间平滑过渡，避免宽度突跳。实际参数应兼顾游戏规模，不宣称它就是现实河道比例。

汇流区使用公共几何补片：保留公共水面和出流断面，平滑接入两条支流，验证河床始终低于水面、外岸足以约束水体。若存在明显高差，明确生成跌水/瀑布连接，而不是把高支流端点悬在空中。

跨区域保存稳定节点/河段 ID、边界位置、切向、断面、水位和水沙边界量。改变 Minecraft 区块加载顺序不得改变这些值。

## 沉积与方块精度

普通完整地形方块的几何显示以格为单位；原版水层、雪层等状态虽有更细的视觉高度，也不能替代通用泥沙体积表达。计算层使用小数体积/质量，最终导出时量化，并保存余量。

例如同一个可沉积单元连续收到 0.2 格体积的散体沉积，五次后才足够显示一个完整方块；前三次的 0.6 不能被舍弃。若输运量记录的是固体体积，需先按孔隙率换算散体体积：`V散体=V固体/(1-孔隙率)`，不能把二者混记。

三角洲优先级最高，宽阔区域容易累积出可见形态。河流内弯沙洲、河床沙砾滩、地下湖底也可显示沉积；窄溪流以河床材料和较大尺度沉积斑块表现为宜。不可为了多显示几个方块而虚增泥沙。

三角洲既需要入海供沙，也需要输沙能力降低/沉降与可沉积空间；把所有泥沙直接贴在河口不等于三角洲过程。海面保持 Y=62，足够厚的水下沉积才能露出水面。

## 维护与验证边界

新算法采用独立领域模型、验证器、求解器、几何接口和导出器，纯 Java 核心不依赖 Minecraft 类型。明确配置和结果不可变，物理量带单位命名，测试名描述规则，避免继续增加模式字符串条件分支。

首批检查：有向无环连通图、公共节点一致、自由水面坡度、流量合并、湖泊库存、接触门控、侵蚀阈值、小数沉积余量和泥沙预算。随后必须检查与真实基础地形的可行性、河床/水面/洞顶三者关系、贯通后的体素连通性、跨区顺序独立性及 Minecraft 水更新行为。

原版方块水流不承担整个流域的物理求解。先离线生成河槽及水体，再单独验证水更新、源水布置和边界封闭；原型的水沙守恒不能证明游戏中不会出现悬河。

当前模型导入使用 30 米/模型像素 → 2 方块/像素、6 米/竖向方块，水平和竖向压缩不同。物理坡度、面积和体积不能直接混用这套源数据单位与游戏坐标。必须选择在原始物理坐标求解后映射，或在明确的游戏空间度量中重新标定；两种结果不可混称真实尺度模拟。
