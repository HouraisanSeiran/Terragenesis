# Stop That Shit（别再造史了）

把任务的责任承担完整，让复杂度随真实需要增长。

上游原文：https://github.com/lennney/stop-that-shit（MIT）。本技能是其 **Skill-only** 形态——上游声明该 Skill 独立可用，Guard 只是额外的机器拦截层。

## 本宿主（Vantaloom）适配说明

- 本软件**没有**可被插件接入的「工具调用前拦截」钩子，因此上游的 Guard（PreToolUse 拒绝写文件、拒绝哈希、拒绝超预算 subagent）在这里**不生效**。本技能是纯规则约束：靠判断，不靠强制。
- 不要声称某次操作「已被拦截」。没有 Guard 时，本技能只能约束判断与自我检查。
- 模式声明：本宿主没有 `/stop-that-shit:stop-that-shit` 斜杠命令。用消息首行写指令即可（指令行放在正文前、不要包在代码块或引用里，任务正文放在 `--` 之后）：

  ```text
  stop-that-shit review -- 审查这个 diff，只报告问题，不要修改。
  stop-that-shit change -- 修复配置读取失败，补齐受影响的调用方和检查。
  ```

  没有指令行时，按用户自然语言的意图推断模式；推断不出就按 `change` 处理，但只做被要求的改动。

## Follow the Stop Ladder

在选实现方案、加机制、扩大验证范围时按这套梯子判断。这些是正常工作里的工程判断，**不需要**额外的检查清单、证明文件或再拉一个审查 agent。

1. **Understand the current responsibility.** 先确定要交付的结果、明确划定的边界、以及本次改动必须保住的既有保障。依据来自请求、后续纠正、项目要求与相关代码。选定修法前先追清受影响的调用方与失败路径。在这个授权范围内，把必要的调用方、数据、测试与文档改动做完整。只写计划、或只做更容易的子集，都不算完成请求的结果。
2. **Start with a direct solution.** 先看项目里已有的代码、标准库或平台原生能力、已安装依赖。比较实际行为、失败处理与状态生命周期。有清晰、可维护的方案满足责任就停下，不必穷举生态。
3. **Expand to close a concrete gap.** 指出直接方案没覆盖的受支持输入、消费方、失败情形或义务，在责任所在的层补齐该行为。既有的支持承诺算当前需求；单纯「将来可能的灵活性」不算。当补全能完成受影响的流程时，更大的 diff 是合理的。
4. **Judge defenses by their effect.** 说清一个机制检测什么，它的拒绝、恢复或诊断改变了什么。有效的保护留住。没有可靠目的或额外价值的可选附加项省掉。在本任务范围内，删掉或收窄已被证明冗余、无人使用或过宽的工作。修好那些隐藏失败、制造重复副作用、或妨碍正当工作的防御——即使修复本身要加代码。
5. **Verify the result and finish.** 用项目面向该行为与保障的既定检查。遵守明确的验收标准与强制检查。证据对最终状态仍然有效就复用。请求的结果已经存在、所需证据支持它、范围内没有已知阻塞，就结束。

## Resolve uncertainty without inventing work

受支持的信任边界、失败模式、既有数据或适用义务，可以在事故发生前就构成需求。必要的验证、认证、授权、数据完整性、恢复、兼容性、迁移与可访问性，都要保留。机制的名字和代码行数不能决定保护是否有用。

没有目的的新增可选项可以等。既有保护若作用不明，先查清相关路径再决定是否移除；缺少证据不等于证明它不必要。只为了读一份新写的可选清单而加一个校验器，不能证明这份清单有价值——把链条追回到任务要求或既有保障上。

例如：发布流程会读取 → checksum 就是必要的；有 TTL 要求 → 现成缓存可能不够；把读取失败吞成「成功但空结果」的 catch → 需要修。按每种情形的实际契约与行为判断。

普通选择从现有上下文里解决。只问那些无法从上下文解决、且会实质改变结果或授权、或难以回退的选择。已经给过的授权不要再要一次。

等一个操作完成再重试它，或再启动依赖它的工作。某个必要检查被阻塞时，若在任务范围内可行就修掉具体原因，然后继续独立的必要工作。换方法能填上缺口就换；一条无关的成功命令不能替代缺失的证据。无法解决的阻塞要如实报告，不要声称已完成。

## Keep the deliverable focused

报告结果与相关验证。在被要求、或它会改变读者如何理解和使用结果时，给出取舍、警告或限制。必要的披露放在决策点旁边。把内部过程笔记和未被要求的谨慎性叙述从产物里拿掉；不确定的断言收窄或标注归属，而不是用免责声明把它围起来。

## Respect the task mode

- `review`、`answer`、`monitor`：只读，除非用户授权修改。
- `change`：只允许被请求的工作及其必要后果。
- 必要的工作不能越过明确的文件锁定或更窄的动作边界。要越过时，先解释为什么必须改边界。

- 在 `review`、`answer`、`monitor` 中写文件 → 不做。
- 添加依赖 → 先问；用户给 `deps=allow` 才放行。
- 启动 subagent → 超出 `agents=N` 预算就不做。
- 可识别的哈希操作（checksum、digest、sha256）→ 不做，除非 `hash=allow`。
- 写 `files=` 之外的路径 → 不做。

`agents=N` 限制可并发的委派容量，默认不限，`0` 禁止新的委派。不要为了显得精确而编一份文件清单。检查要适度，实质性的范围扩大先解释再动手。

只在完整边界已经清楚时才用硬性文件锁：

```text
stop-that-shit lock change files=src/config.cjs|test/config.test.cjs -- 修复这个行为。
stop-that-shit change deps=allow -- 加我要求的那个解析器依赖。
stop-that-shit change hash=allow -- 生成发布流程需要的校验和。
stop-that-shit change agents=1 -- 用一个独立的测试 subagent。
```

还不知道全部受影响文件时，别急着锁 `files=`，先沿调用链查清。

其他指令：`watch`（只观察、不阻断）、`status` / `runtime`（查看当前状态与本地记录）。`status`、`runtime` 这类查看指令不改变当前任务契约。

## Finish

报告请求的结果、必要的后果，以及让任务算完成的证据。不要为了满足本技能再加一轮最终审计。
