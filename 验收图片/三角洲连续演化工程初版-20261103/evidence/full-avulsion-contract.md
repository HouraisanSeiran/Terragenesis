# Candidate avulsion integration contract

`activate_candidate(state, progress, *, hydraulic_config, sea_level_m=0., min_rise_m=.1, max_cut_m=.5)` returns `(state, progress, report)`. Call once on the initial sections before evolution unless `progress['avulsion_baseline_sections']` already contains the initial `[z,x,bed,width,bank]` nodes. The first call records that baseline through `branching._record` and does not activate a route. Preserve it in checkpoints. The source fingerprint is unchanged.

Subsequent calls compare parent sections downstream of a candidate fork against this baseline. A rise of at least `min_rise_m` is required. Candidates are tried in stored order, at most one activation per call. Their complete path starts at a parent fork. Only unique D4 suffixes with a distinct exterior-ocean face are accepted. Candidate beds derive from current DEM after bounded sediment-only cuts. Trial hydraulics must have positive candidate discharge with every candidate bed below the pre-trial fork stage. Planned shares seed topology; `river_hydraulics`, `actual_shares`, and `active` come from the solver.

`report` has `activated`, `trigger` (baseline_recorded, no_eligible_candidate, or activated), and on success `candidate_index`, `parent`, `fork_index`, `fork`, `rise_m`, `fork_stage_m`, `actual_Q_m3_s`, `solid_cut_m3`, and `excavation` (cell and solid volume). Zero `solid_cut_m3` denotes natural overflow. Failed trials leave the input state and progress unchanged. Records for other inputs and unknown history entries are retained.

Initial hydraulic solver failure returns the unchanged inputs with `trigger=hydraulic_failure`. The acceptance check also requires the post-trial fork stage to exceed each candidate bed. Mixed-area owner stocks, when present, are updated using the same area-fraction convention as integrated evolution.

## Shoreline mouth extension

`extend_mouths(state, progress, *, hydraulic_config, sea_level_m=0., radius_m=2000., max_cut_m=.5)` returns `(state, progress, report)` and does not advance time. It extends currently closed mouths in route order, excluding all existing and newly appended route cells from each search. The radius is Euclidean distance from each old mouth; the search uses the imposed upstream stage limit only as a ceiling, and a full section solve must accept positive discharge and place each affected route section below its own solved water surface. Each new endpoint must have an independent exterior ocean face. Natural routes are tried before sediment cutting. Any unresolvable closed mouth or failed combined trial returns the exact input objects with no partial update.

On success `report` has `extended=True`, `trigger='extended'`, `extensions` (route index, old and new mouths, path, route Q, cut and excavation), `solid_cut_m3`, and `geometry_updates`, a list of `[z,x,bed_m,width_m,bank_m]` rows for new hydraulic nodes. `hydraulic_sections.nodes` is authoritative; `integrated.sections` remains indexed solely by the original main route. `river_hydraulics`, actual shares, activity, segments, control references and area-mixed owner stocks are synchronized. `source_state_fingerprint` and unrelated records remain unchanged. If no extension is needed, `trigger='already_open'`; failure uses `trigger='no_feasible_extension'` or `hydraulic_failure`. Both cases return unchanged inputs and `geometry_updates=[]`.

## Candidate activation after shoreline advance

`activate_candidate` accepts `mouth_radius_m=4000.` as a keyword-only search radius. After a candidate is tentatively added, closed mouths are extended transactionally with `extend_mouths` using the same hydraulic configuration, sea level, and `max_cut_m`. The final solver must report positive candidate flow and every section of the entire final candidate route must be below its own solved stage; endpoints have independent exterior faces. On failure, neither tentative records nor tentative geometry escape. Successful reports retain `solid_cut_m3` as the combined candidate and shoreline cut, add `candidate_solid_cut_m3`, `mouth_solid_cut_m3`, and `mouth_extension` (the extension report, including `geometry_updates`). No extension is represented by an `already_open` report. Repeated calls do not activate a route whose suffix is already occupied.

If pre-existing parent mouths are closed, a temporary parent extension is tried first to obtain real fork stages; it is committed only if a candidate is subsequently accepted. `parent_mouth_extension` reports that work separately, and its cut is included in `mouth_solid_cut_m3` and `solid_cut_m3`.
